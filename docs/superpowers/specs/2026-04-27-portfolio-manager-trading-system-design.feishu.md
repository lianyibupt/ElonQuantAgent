# 组合经理型交易系统设计（飞书版）

日期：2026-04-27
项目：ElonQuantAgent
分支：design/portfolio-manager-system

---

## 一、设计目标

将当前项目从“单票技术分析系统”升级为“面向个人美股账户的实盘交易助手”。

目标系统需要同时具备：

- 单票趋势与入场分析
- 账户级仓位控制
- 组合风险管理
- 基金经理视角的配置建议
- 核心仓 + 战术仓的双账本框架

该系统面向以下真实使用场景：

- 用户使用个人实盘账户交易
- 主要市场为美股
- 后续可以考虑少量港股，但不是第一阶段重点
- 核心仓持有周期约 6 个月
- 战术仓用于周级别趋势交易
- 用户重视回撤控制，希望把账户最大痛苦回撤控制在 15% 左右

---

## 二、核心判断：当前系统的问题不在指标，而在决策层级

当前项目已有：

- indicator agent
- pattern agent
- trend agent
- decision agent
- `core/trading_graph.py` 单票串行分析流程

当前系统的优势：

- 已经具备模块化分析结构
- 能输出技术指标、图形和趋势解释
- 已支持 Web 与程序化调用

但当前系统仍存在明显不足：

- 最终输出仍停留在 LONG / SHORT 粗粒度层面
- 没有账户状态和组合状态
- 没有风险预算层
- 没有核心仓 / 战术仓区分
- 没有市场状态控制总仓位
- 没有相关性和集中度管理
- 没有“账户经理看板”

因此，当前项目更像“单票分析器”，还不是“账户级交易系统”。

---

## 三、产品方向：从单票分析器升级为双层组合系统

系统需要回答两个不同层次的问题：

1. 这只股票单独看是否值得做？
2. 在当前账户和当前风险预算下，这只股票是否还值得做？

这两层必须分开处理。

推荐方向：

**双层组合系统 + 市场状态驱动风控**

原因：

- 最符合用户“实盘 + 经理型”的真实需求
- 能同时兼容长期核心仓与周级战术仓
- 能直接围绕 15% 回撤目标设计风险体系
- 可在现有项目基础上渐进式改造

---

## 四、目标架构

### 4.1 四层结构

目标系统应包含四层：

1. 市场状态层（Market Regime Layer）
2. 单票评分层（Single-Name Scoring Layer）
3. 组合构建层（Portfolio Construction Layer）
4. 执行决策层（Execution Decision Layer）

### 4.2 市场状态层

作用：

- 判断当前是进攻、选择性进攻、中性还是防守
- 先给出总仓位与战术仓位上限，再决定是否允许新增交易

输出：

- 当前市场状态
- 建议总仓位区间
- 建议战术仓区间
- 允许新增风险的强度
- 是否限制低质量机会

### 4.3 单票评分层

作用：

- 用结构化评分卡替代 LONG / SHORT
- 继续复用 indicator / pattern / trend 三类底层分析
- 将 decision agent 改造成单票评分器

每只票的输出应包括：

- 趋势质量
- 入场质量
- 估值 / 拉伸状态
- 催化质量
- 波动性认知
- 与当前账户的相关性惩罚
- 组合适配度
- 推荐账本：核心仓 / 战术仓
- 推荐动作：买、加、持有、减、退、观察、禁止新增

### 4.4 组合构建层

作用：

- 综合市场状态、账户状态、持仓状态和单票评分
- 生成账户级决策

负责判断：

- 当前是否还能加风险
- 可以分配多少资金
- 某个机会应进入核心仓还是战术仓
- 是否因集中度或相关性过高而被阻断
- 是否应该先降风险，而不是继续进攻

### 4.5 执行决策层

作用：

- 把上层决策输出成可执行动作

输出包括：

- 账户经理指令
- 单票交易建议单
- 允许动作的解释
- 禁止动作的解释

## 五、账户框架

### 5.1 核心仓

定位：

- 中期和长期持有
- 持有周期可达 3 到 6 个月甚至更久
- 用于承载高确信度主线资产和趋势逻辑

建议：

- 常态占比：50% - 70%
- 单票初始仓位：8% - 12%
- 单票上限：约 15%

### 5.2 战术仓

定位：

- 周级别趋势交易
- 用于突破、回踩、催化延续等机会

建议：

- 常态占比：10% - 30%
- 单票初始仓位：3% - 6%
- 单票上限：约 8%

### 5.3 现金储备

定位：

- 主动风险缓冲，不是被动剩余

建议：

- 常态现金：10% - 20%
- 防守期现金：30% - 50%

---

## 六、风险预算体系

### 6.1 单笔风险预算

每笔交易先定义：

- 入场价
- 失效价 / 止损位
- 允许亏损占 NAV 比例

建议：

- 核心仓单笔风险：0.75% - 1.25% NAV
- 战术仓单笔风险：0.35% - 0.75% NAV

原则：

仓位大小必须由风险预算和止损距离推导，而不是拍脑袋决定。

### 6.2 账户总风险预算

建议约束：

- 如果所有止损同时触发，理论总损失应大体控制在 4% - 6% NAV 内

### 6.3 回撤防线

#### 正常模式

- 按标准规则运作

#### 预警模式（回撤约 6% - 8%）

- 提高新仓质量门槛
- 降低战术仓上限
- 增加现金
- 不再做低质量试错

#### 防守恢复模式（回撤约 10% - 12%）

- 先降风险，后谈进攻
- 明显限制高 beta 仓位
- 以保护净值为第一目标
- 将 15% 视为硬红线

## 七、市场状态机

### 7.1 Risk-On

特征：

- 风险资产趋势良好
- 龙头持续强势
- 波动可控

动作：

- 提高总仓
- 允许战术仓积极参与

### 7.2 Selective Risk-On

特征：

- 只有少数主线真正赚钱
- 强势集中、轮动快

动作：

- 只做最强主线
- 战术仓可参与，但必须精选

### 7.3 Neutral

特征：

- 市场震荡
- 趋势持续性差

动作：

- 降低总仓
- 降低战术仓进攻性
- 提高新仓门槛

### 7.4 Risk-Off

特征：

- 市场趋势受损
- 波动显著上升
- 高 beta 同步走弱

动作：

- 明显降低总仓
- 压缩战术仓
- 提高现金、保护账户

---

## 八、代理股与因子映射

从用户的实际交易风格看，系统必须识别“表面不同、实质同方向”的仓位重叠。

典型映射示例：

- MSTR → BTC proxy
- SBET / 类似标的 → ETH / treasury 风格 crypto-beta
- 平台龙头 → mega-cap tech beta
- PDD / 类似标的 → China ADR beta

建议引入因子映射层，将标的映射到：

- BTC beta
- ETH beta
- mega-cap tech beta
- China ADR beta
- event-driven beta
- rate-sensitive beta

目标：

识别隐藏集中度，避免多个不同 ticker 在账户中形成同一个方向的重复杠杆。

---

## 九、组合硬规则

### 9.1 总仓位上限（按状态）

- Risk-On：70% - 85%
- Selective Risk-On：55% - 75%
- Neutral：35% - 60%
- Risk-Off：15% - 35%

### 9.2 战术仓位上限（按状态）

- Risk-On：25% - 30%
- Selective Risk-On：允许，但更精选
- Neutral：10% - 15%
- Risk-Off：0% - 5%

### 9.3 因子组暴露上限

- BTC proxy：约 25% - 30%
- ETH proxy：约 20% - 25%
- 任意高相关主题组：约 35% - 40%

### 9.4 波动率感知的单票上限

单票最大仓位应受以下因素共同影响：

- 波动率
- 与现有持仓的相关性
- 核心仓 / 战术仓属性

### 9.5 回撤触发自动降档

当账户进入预警或防守阈值时，系统必须自动降低风险偏好。

## 十、单票评分卡设计

建议用六维评分卡替代 LONG / SHORT：

1. 趋势分
2. 入场质量分
3. 估值 / 拉伸分
4. 催化分
5. 相关性惩罚
6. 账本适配分

每只票应输出：

- 是否可交易
- 核心仓 / 战术仓适配性
- 建议仓位区间
- 入场区
- 失效价
- 第一 / 第二止盈目标
- 若账户已有过多相关暴露，是否阻断新增

核心原则：

> 一只股票方向对，不等于它在当前账户里还值得继续加仓。

## 十一、输出设计

### 11.1 账户经理看板

必须优先展示：

- 今天是什么市场状态
- 当前建议总仓位
- 当前建议战术仓位
- 哪些因子已经过于拥挤
- 当前还剩多少新增风险预算
- 今日最重要的经理动作

建议固定字段：

- NAV
- 当前总仓
- 现金占比
- 核心仓占比
- 战术仓占比
- 当前回撤
- 近期波动
- 当前市场状态
- 状态判断依据
- 建议总仓位区间
- 剩余风险预算
- 因子暴露拆解
- 集中度预警
- 今日经理动作

### 11.2 单票交易建议单

每张卡片建议包含：

- ticker
- 角色：核心仓 / 战术仓 / 暂不适合
- 总评分
- 市场适配度
- 账户适配度
- 当前动作：买、加、持有、减、退、观察、禁止新增
- 趋势判断
- 入场类型
- 建议仓位
- 入场区间
- 失效价
- 止盈目标
- 触发条件
- 阻断原因
- 与当前持仓相关性
- 是否占用拥挤因子预算
- 是否处于过热 / 拥挤状态

### 11.3 “禁止新增”的理由必须明确输出

系统应能明确写出：

- 趋势仍强，但与现有 crypto-beta 仓位重合度过高
- 估值和情绪过热，不适合追涨
- 当前状态下战术仓预算不足
- 当前账户已进入防守模式，不能新增高 beta 仓位

## 十三、实现前置依赖 Checklist

在开始实现 `regime_agent`、`portfolio_manager_agent` 和账户级决策流水线之前，项目需要先补齐一组最小前置依赖。这些内容不是可有可无的润色项，而是避免系统重新退化成“单票分析 + 组合话术”的基础层。

### 13.1 必须先完成的前置项

#### 1. 账户状态输入结构

系统必须先定义统一的账户输入格式，否则无法进行仓位管理、回撤控制和组合层决策。

最低需要包含：

- 当前 NAV
- 可用现金
- 当前持仓列表
- 每笔持仓的市值、成本和浮盈亏
- 核心仓 / 战术仓分类
- 止损位或 thesis 失效位
- 最近净值高点或稳定的回撤计算基准

验收标准：

- 账户状态以结构化类型输入，而不是自由文本描述
- 系统能稳定计算总仓位、现金占比、核心仓占比、战术仓占比和当前回撤

#### 2. 持仓结构与候选池结构

系统必须区分“已有持仓复评”和“新机会评分”，否则无法做真正的账户级排序与阻断。

最低需要两类结构：

- `positions`：当前持仓
- `candidates`：待评估候选标的

每个标的至少应包含：

- ticker
- 市场
- 当前价格
- 预期账本类型（如已知）
- 主题 / 因子标签，第一版可人工维护
- 当前账户是否已有暴露

验收标准：

- 同一套评分流程既能处理持仓，也能处理新候选
- 组合层能清楚区分加仓、持有、减仓、退出，与新开仓、禁止新增两类动作

#### 3. 因子映射与代理暴露表

这是本系统面向该用户最关键的前置条件之一。没有这层映射，系统无法识别“不同 ticker，本质同一个方向”的隐藏集中度。

第一版不需要自动化，但必须先有可维护的人工映射表。

建议首批因子桶：

- BTC beta
- ETH beta
- mega-cap tech beta
- China ADR beta
- event-driven beta
- rate-sensitive beta

示例映射：

- MSTR → BTC beta
- SBET → ETH / treasury 风格 crypto beta
- PDD → China ADR beta

验收标准：

- 每个持仓和候选标的都能映射到 1 到 2 个主因子桶
- 系统能统计各因子桶当前暴露占比
- 组合层可以据此阻断隐藏的重复加仓

#### 4. 市场状态输入源

没有 regime 输入，系统就无法贯彻“先定账户进攻度，再决定是否准许交易”的核心设计。

第一版不需要复杂宏观模型，但必须有一套稳定、可重复的输入框架。

建议输入：

- 主要指数趋势代理
- 宽度或 leadership 代理
- 波动率代理
- 与用户重点主题相关的风险代理，例如 BTC、ETH

验收标准：

- 系统能稳定输出四种状态之一：Risk-On、Selective Risk-On、Neutral、Risk-Off
- 每种状态都能映射到默认的总仓与战术仓区间

#### 5. 单票评分卡 Schema

在组合层工作前，单票输出必须先从 LONG / SHORT 升级为结构化评分卡。

第一版最低需要：

- `trend_score`
- `entry_score`
- `valuation_stretch_score`
- `catalyst_score`
- `volatility_score`
- `correlation_penalty`
- `portfolio_fit_score`
- `recommended_book`
- `recommended_action`
- `invalidation_price`
- `suggested_position_range`

验收标准：

- 持仓和候选统一输出同一套 schema
- 组合层消费结构化字段，而不是解析自由文本 LONG / SHORT 结论

#### 6. 风险参数配置表

核心硬规则必须先落到配置层，而不是埋在 prompt 或散落在代码常量里。

最低应配置：

- 各市场状态下的总仓上限
- 各市场状态下的战术仓上限
- 核心仓 / 战术仓初始仓位建议
- 核心仓 / 战术仓单笔风险预算
- 因子暴露上限
- 预警 / 防守回撤阈值

验收标准：

- 所有关键阈值都可以集中查看和修改
- portfolio manager 输出引用同一套参数来源

### 13.2 第一轮实现中强烈建议同步补齐的能力

#### 7. NAV 与回撤计算逻辑

系统需要明确回撤逻辑：

- NAV 是按日频还是事件频跟踪
- 最近净值高点如何定义
- 是否纳入未实现盈亏
- 账户回撤与单票回撤是否分开处理

验收标准：

- 给定持仓和 NAV 时间序列，系统能稳定输出当前回撤与回撤分档
- 回撤分档能自动触发预警或防守模式

#### 8. 最小回放与场景验证框架

这个系统不仅要验证“分析对不对”，还要验证“账户决策安不安全”。

第一版不需要完整量化回测，先做场景回放就足够有价值。

最低能力：

- 读取样例账户状态
- 读取样例市场状态
- 读取一组候选评分卡
- 生成组合指令
- 验证是否违反硬约束

代表性场景至少包括：

- Risk-On 且仍可继续加风险
- Selective Risk-On 且主线狭窄
- Neutral 且机会质量分化
- Risk-Off 下即使单票强也被账户层阻断
- 多个 crypto proxy 导致集中度超限

#### 9. 稳定的账户经理输出模板

应尽早冻结第一版账户经理看板和交易建议单结构，避免后期输出层反复漂移。

最低模板包括：

- 账户经理看板字段
- 单票交易建议单字段
- blocked candidate 的解释字段
- forced trim 的解释字段

验收标准：

- 输出结构跨运行保持稳定
- 用户能直接看懂今天能不能加风险、该加什么、什么被阻断

### 13.3 可以后续渐进增强的项

#### 10. 因子映射自动化

第一版可人工维护，后续再增强为：

- 基于规则的 symbol tagging
- 基于相关性的辅助归类
- 基于主题库的自动映射

#### 11. 券商或执行接口集成

第一阶段不需要自动下单。

后续再考虑：

- 自动同步持仓
- 导出订单建议
- 券商 API 联动

#### 12. 更完整的估值与基本面模块

初版应优先把精力放在：

- 趋势质量
- 入场质量
- 暴露重叠
- 组合风险预算

估值层第一版只需覆盖拉伸、过热和 premium risk 感知。

### 13.4 建议实现顺序

实现时应按以下顺序推进，而不是所有层并行摊开：

1. 账户与持仓数据结构
2. 候选池结构
3. 因子映射表
4. 单票评分卡 schema
5. 市场状态输入与状态机
6. 风险参数配置

### 13.5 实现准备度门槛

## 十五、TradingGraph 的演进

### 阶段 A：单票分析流水线

对每个候选标的 / 当前持仓执行：

- 指标分析
- 形态分析
- 趋势分析
- 单票评分

### 阶段 B：组合决策流水线

统一输入：

- 市场状态
- 账户状态
- 当前持仓
- 候选标的评分卡
- 持仓复评评分卡

输出：

- 组合指令
- 单票建议单

系统将从：

- 单票输入 → 单票结论

升级为：

- 账户上下文 + 多票输入 → 组合指令 + 交易清单

## 十六、渐进式实现顺序

第一、第二阶段承载了绝大部分实际价值，应优先保证这两段落地质量。

### 第一阶段

这是价值最高的第一步，因为它在不立即引入完整组合层的前提下，就能把现有引擎升级成可被后续账户层消费的标准化模块。

- 建立 `AccountState` 和 `PositionState`
- 定义候选池输入结构
- 建立第一版因子映射表
- 把 LONG / SHORT 升级成评分卡
- 做核心仓 / 战术仓归类
- 增加入场、止损、仓位结构

### 第二阶段

这是第二个高价值阶段，因为它把系统从“更好的单票分析器”推进成“真正可用的账户助手”。

- 加入账户与持仓输入流程
- 加入总仓、现金、核心仓、战术仓统计
- 加入主题 / 因子暴露统计
- 加入市场状态判断
- 加入账户级风险预算与回撤分档
- 输出第一版经理看板

这一阶段完成后，系统应能回答：

- 今天账户还能不能加风险
- 应该加哪类风险，避免哪类风险
- 当前是否在某个隐藏因子桶中过于拥挤

### 第三阶段

- 加入相关性阻断
- 加入因子组暴露上限
- 加入回撤触发降档逻辑
- 加入 blocked candidate / forced trim 输出

## 十七、测试策略

测试必须覆盖两类问题：

1. 分析是否正确
2. 决策是否安全

建议测试：

- 单票评分卡 schema 测试
- 核心仓 / 战术仓归类测试
- 回撤与仓位统计测试
- 市场状态仓位上限测试
- 因子集中度识别测试
- 超限条件下阻断新仓测试
- 回撤降档测试
- 端到端场景测试

---

## 十八、第一阶段非目标

首阶段不做：

- 完整港股支持
- 全量基本面模型
- 期权组合管理
- 税务优化
- 机构级优化器数学模型
- 对所有资产类别的泛化支持

第一阶段只聚焦用户当前最真实的工作流。

---

## 十九、最终总结

项目应从“单票技术分析器”演进为“具备组合感知和账户决策能力的实盘交易系统”。

最终结构：

- 底层：指标、形态、趋势 → 单票评分卡
- 上层：市场状态、账户状态、因子暴露、组合风险管理
- 输出：账户经理看板 + 单票交易建议单

核心设计原则：

> 一只股票单独看很有吸引力，并不代表它在当前账户中仍然是正确的交易。

这条原则应贯穿后续所有实现和评估工作。
