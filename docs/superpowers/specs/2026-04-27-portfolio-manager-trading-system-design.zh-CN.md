# 组合经理型交易系统设计

日期：2026-04-27  
分支：design/portfolio-manager-system  
项目：ElonQuantAgent

## 1. 目标

将当前项目从“单票技术分析系统”升级为面向个人美股账户的实盘交易助手。目标系统需要同时具备以下能力：

- 单票趋势与入场分析
- 账户级仓位管理
- 组合风险控制
- 基金经理视角的配置建议
- 支持“核心仓 + 战术仓”的混合持仓框架

该设计面向的用户主要交易美股，未来可再考虑少量港股；目标是做一个真正能辅助实盘的系统，并尽量把账户级回撤控制在用户更能接受的 15% 左右。

## 2. 用户画像与投资背景

系统围绕以下用户约束和偏好设计：

- 使用个人实盘账户，而不是纸面交易或纯研究环境
- 主要市场：美股
- 次要市场：港股，暂不纳入第一阶段
- 混合持有周期：
  - 核心仓可持有约六个月
  - 战术仓用于周级别趋势交易
- 混合选股范围：
  - 可持有大盘核心资产
  - 也会交易高 beta、强叙事、事件驱动的标的
- 期望输出：
  - 既有单票交易建议，也有账户经理视角的组合建议
- 回撤偏好：
  - 历史上出现过约 25% 的回撤
  - 目标系统应尽量把回撤更稳定地压在 15% 的舒适区附近

另外，从用户提供的 Gemini 聊天记录可以看出，用户常交易的并不是普通股票，而是“资产代理股 / 主题代理股”。例如 MSTR、SBET，以及 PDD、CRCL 等标的。这意味着系统不仅要建模股票本身，还要建模背后的底层因子和代理暴露。

## 3. 当前项目评估

当前仓库是一个价格驱动的多 Agent 分析系统，主要组件包括：

- indicator agent
- pattern agent
- trend agent
- decision agent
- 在 `core/trading_graph.py` 中串联的单票顺序分析流程

当前优势：

- 已经具备分层分析结构
- 能计算并解释技术指标和图形形态
- 已经支持 Web 和程序化调用
- 已经具备偏交易导向的自然语言输出能力

当前不足：

- 最终输出仍然过于粗糙，主要停留在 LONG/SHORT 层面
- 没有显式的账户状态、组合状态和风险预算层
- 没有核心仓 / 战术仓的概念
- 没有通过市场状态控制总仓位
- 没有对相关标的的集中度和相关性做约束
- 没有账户经理视角的总览看板

所以，当前项目更像一个单票分析引擎，而不是一个账户级决策系统。

## 4. 产品方向

项目应演进为一个“双层组合交易系统”：

- 底层：对单个机会进行评分和分类
- 上层：管理风险、资本配置和账户级决策

系统需要依次回答两个问题：

1. 这只股票单独看是否有吸引力？
2. 这只股票放进当前账户和当前风险预算里，是否仍然值得做？

这两者的区别，是整个系统设计的核心原则。

## 5. 推荐方案

曾考虑过三类大方向：

1. 只强化单票预测引擎
2. 构建“市场状态驱动风险控制”的双层组合系统
3. 优先做账户经理看板，把交易建议放在次要位置

推荐方案：**双层组合系统 + 市场状态驱动风控**。

选择原因：

- 最符合用户真实工作流：实盘交易 + 组合管理
- 能自然支持核心仓与战术仓并存
- 能直接解决最重要的问题：把回撤更稳定地控制在可接受范围内
- 可以在现有仓库基础上渐进式落地，而不是推翻重来

## 6. 目标架构

### 6.1 高层分层

目标系统应包含四个逻辑层：

1. **市场状态层（Market Regime Layer）**
2. **单票评分层（Single-Name Scoring Layer）**
3. **组合构建层（Portfolio Construction Layer）**
4. **执行决策层（Execution Decision Layer）**

### 6.2 市场状态层

目的：

- 判断系统当前处于进攻、选择性进攻、中性还是防守状态
- 在评估单票之前，先给出自上而下的总仓位约束

可能输入：

- 主要指数趋势状态
- 板块和市场宽度代理指标
- 波动率代理指标
- 与账户相关主题的风险资产联动情况
- 在管理 crypto-beta 股票时可选接入 BTC / ETH 等代理输入

输出：

- 市场状态分类
- 建议总仓位区间
- 建议战术仓位区间
- 新增风险的允许强度
- 对弱势 setup 的状态性限制

### 6.3 单票评分层

目的：

- 用结构化评分卡替代粗糙的 LONG/SHORT 结论，对候选标的和现有持仓都做统一评估

该层仍应复用现有分析基础：

- indicator agent
- pattern agent
- trend agent

但当前的 decision agent 应被重定义为标准化的单票评分器。

每只股票必须输出：

- 趋势质量
- 入场质量
- 估值 / 拉伸状态
- 催化质量
- 波动性认知
- 相对当前账户的相关性惩罚
- 组合适配度
- 推荐账本类型：核心仓 / 战术仓
- 推荐动作：买入、加仓、持有、减仓、退出、观察、禁止新增

### 6.4 组合构建层

目的：

- 将市场状态、账户状态、当前持仓和单票评分统一组合成账户级决策集

这一层需要决定：

- 当前是否允许继续新增风险
- 可分配多少资金
- 某个标的应该进入核心仓还是战术仓
- 某个机会是否因为集中度或相关性约束而被阻断
- 即使某些单票看起来不错，账户整体是否仍需要优先降风险

### 6.5 执行决策层

目的：

- 将组合层决策转成用户可以直接拿来执行的交易指令

输出必须包括：

- 组合级指令
- 单票交易建议单
- 对允许动作的解释
- 对被阻断动作的解释

## 7. 账户框架

### 7.1 核心仓

核心仓用于中期和更长期持有，通常是三到六个月甚至更久。

特征：

- 用于承载高确信度趋势或长期主线逻辑
- 换手率较低
- 对正常波动有更高容忍度
- 适合大盘龙头或强结构性主线

建议常态占比：

- 账户风险资产的 50% 到 70%

建议初始仓位和上限：

- 初始仓位通常 8% 到 12%
- 上限约 15%，但需受波动率和集中度约束

### 7.2 战术仓

战术仓用于周级别趋势交易，围绕突破、回踩、催化驱动等节奏做更灵活的操作。

特征：

- 仓位更小
- 止损更快
- 更强调赔率与节奏，不强调长期陪伴

建议常态占比：

- 账户风险资产的 10% 到 30%

建议初始仓位和上限：

- 初始仓位通常 3% 到 6%
- 上限约 8%，但仍受波动率和相关性约束

### 7.3 现金与防守储备

现金不是剩余仓位，而是主动风险储备。

建议常态占比：

- 10% 到 20%

在防守状态下，现金可提高到：

- 30% 到 50%

## 8. 风险预算框架

### 8.1 单笔交易风险预算

每一笔交易都应先定义：

- 入场价
- 失效价 / 止损位
- 允许亏损占账户净值的比例

建议范围：

- 核心仓单笔风险：0.75% 到 1.25% NAV
- 战术仓单笔风险：0.35% 到 0.75% NAV

仓位大小应由“可承受风险”和“止损距离”推导，而不是拍脑袋决定。

### 8.2 账户总风险预算

系统还必须跟踪所有持仓在止损层面的总风险。

建议控制：

- 如果所有止损同时触发，理论账户损失应大体控制在 4% 到 6% NAV 内

这应当成为是否允许继续开新仓的硬约束。

### 8.3 回撤防线分级

由于用户对超过约 15% 的回撤较为敏感，系统应内置三阶段回撤防线。

#### 第一阶段：正常运行

- 按标准市场状态和风险规则运行
- 使用核心仓、战术仓和现金的目标配置

#### 第二阶段：预警模式

当账户从近期高点回撤约 6% 到 8% 时触发。

动作：

- 提高新仓最低质量门槛
- 下调战术仓上限
- 增加现金储备
- 避免低质量或低确信度加仓

#### 第三阶段：防守与恢复模式

当回撤达到约 10% 到 12% 时触发。

动作：

- 优先降风险，不再优先进攻
- 大幅限制高 beta 试错仓位
- 以保住净值和降低暴露重叠为核心
- 将 15% 回撤红线视为硬目标

## 9. 市场状态机

系统应将市场划分为四种状态。

### 9.1 Risk-On（进攻期）

特征：

- 主要风险资产趋势良好
- 龙头标的有持续跟随
- 波动率可控
- 市场具备广度或主线支撑

含义：

- 可提高总仓位
- 允许战术仓参与强势突破和趋势延续

### 9.2 Selective Risk-On（选择性进攻期）

特征：

- 指数层面未必全面强
- 只有少数主题真正赚钱
- 强势集中在狭窄领导板块

含义：

- 只允许做最强主线
- 战术仓仍可参与，但必须更精选
- 避免把仓位分散到中等质量机会

### 9.3 Neutral（中性观察期）

特征：

- 市场偏震荡
- 突破持续性变差
- 趋势延续性下降

含义：

- 下调总仓位
- 保留更强的核心持仓
- 降低战术仓激进度
- 提高新开仓门槛

### 9.4 Risk-Off（防守期）

特征：

- 指数或主线趋势受损
- 波动率抬升
- 高 beta 标的和代理股同步走弱

含义：

- 明显降低总仓位
- 压低战术仓占比
- 优先提升现金、回收风险和保护账户

## 10. 代理暴露与因子映射

对于该用户而言，最关键的要求之一，是识别“看起来不同的股票，其实押的是同一个方向”。

例如：

- MSTR 作为 BTC 代理
- SBET 及类似标的作为 ETH / treasury 风格 crypto-beta 代理
- 大型平台股作为 mega-cap tech beta
- PDD 及类似标的作为 China ADR 暴露

因此，系统应包含一个风险映射层，把每个持仓和候选标的映射到一到两个核心因子桶，例如：

- BTC beta
- ETH beta
- mega-cap tech beta
- China ADR beta
- event-driven beta
- rate-sensitive beta

该映射的目的，是识别隐藏集中度，避免表面看起来分散、实质上却在同一方向上重复加杠杆。

## 11. 硬性组合规则

组合经理层应执行明确的硬约束。

### 11.1 按市场状态控制总仓上限

默认参考区间：

- Risk-On：70% 到 85%
- Selective Risk-On：55% 到 75%
- Neutral：35% 到 60%
- Risk-Off：15% 到 35%

### 11.2 按市场状态控制战术仓上限

默认参考区间：

- Risk-On：25% 到 30%
- Selective Risk-On：允许，但必须精选
- Neutral：10% 到 15%
- Risk-Off：0% 到 5%

### 11.3 因子组暴露上限

默认参考上限：

- BTC proxy 暴露：不超过约 25% 到 30%
- ETH proxy 暴露：不超过约 20% 到 25%
- 任意高相关主题组：不超过约 35% 到 40%

具体阈值应保持可配置。

### 11.4 波动率感知的单票上限

单票最大仓位应根据以下维度动态调整：

- 已实现或隐含波动率代理
- 与组合其余部分的相关性
- 属于核心仓还是战术仓

同样是 10% 仓位，配在宽基 ETF 和配在高波动代理股上，风险完全不同。

### 11.5 基于回撤的自动降档

当账户回撤进入预警或防守阈值时，系统必须自动降低激进程度。

## 12. 单票评分卡设计

当前的 LONG/SHORT 风格输出应被替换为六维评分卡。

建议维度：

1. **趋势分（Trend Score）**
2. **入场质量分（Entry Quality Score）**
3. **估值 / 拉伸分（Valuation/Stretch Score）**
4. **催化分（Catalyst Score）**
5. **相关性惩罚（Correlation Penalty）**
6. **账本适配分（Book Fit Score）**

每只标的都应输出统一结构，包括：

- 是否可交易
- 更适合核心仓还是战术仓
- 建议仓位区间
- 建议入场区
- 失效价
- 第一和第二止盈目标
- 如果账户已有过多相关暴露，是否应被阻断

关键规则：

> 一只股票单独看方向是对的，并不代表它在当前账户中仍值得继续加仓。

## 13. 输出设计

最终输出必须始终拆成两个视图。

### 13.1 账户经理看板

该视图应放在最前面，并优先回答：

- 今天市场处于什么状态？
- 账户今天应该带多少总仓？
- 允许多少战术仓暴露？
- 哪些因子暴露已经过于拥挤？
- 今天还能新增多少风险预算？
- 今天最重要的经理动作是什么？

建议固定字段：

- 账户净值（NAV）
- 当前总仓位
- 现金占比
- 核心仓占比
- 战术仓占比
- 当前回撤
- 近期账户波动
- 当前市场状态
- 市场状态判断依据
- 建议总仓位区间
- 剩余风险预算
- 因子暴露拆解
- 集中度预警
- 今日关键经理动作

### 13.2 单票交易建议单

每个候选标的和当前持仓都应展示为结构化交易卡片。

建议字段：

- ticker
- 角色：核心仓 / 战术仓 / 暂不适合
- 总评分
- 市场适配度
- 账户适配度
- 当前动作：买入、加仓、持有、减仓、退出、观察、禁止新增
- 趋势判断
- 入场类型：突破买入、回踩买入、仅持有不追、等待确认等
- 建议仓位
- 入场区间
- 失效价
- 止盈目标
- 触发条件
- 若被阻断，则给出原因
- 与当前组合的相关性等级
- 是否占用了已拥挤的风险因子预算
- 当前是否处于过热或拥挤状态

### 13.3 “拒绝交易理由”必须是一等输出

系统必须能清楚解释：为什么某只股票虽然趋势仍然不错，但当前不能再加。

例如：

- 趋势为正，但与现有 crypto-beta 仓位暴露重叠过高
- 估值和情绪过热，不适合追新仓
- 当前市场状态下，战术仓预算不足
- 当前账户已进入回撤防守模式，不能新增高 beta 风险

这种“不给做”的能力，对于抑制情绪化加仓尤其重要。

## 14. 数据模型

当前项目的 state 结构过于偏单票。目标设计需要新增四类主要结构。

### 14.1 AccountState

用于跟踪账户整体状态，例如：

- 总资产 / NAV
- 可用现金
- 当前持仓
- 近期净值高点
- 当前回撤
- 核心仓使用比例
- 战术仓使用比例

### 14.2 PositionState

用于跟踪每一笔持仓，例如：

- ticker
- 持股数量
- 市值
- 浮动盈亏
- 持有天数
- 账本类型
- 因子 / 主题映射
- 止损位
- thesis 状态

### 14.3 SingleNameScore

用于跟踪单票结构化分析结果，例如：

- trend_score
- entry_score
- valuation_stretch_score
- catalyst_score
- volatility_score
- correlation_penalty
- portfolio_fit_score
- recommended_book
- recommended_action

### 14.4 PortfolioDirective

用于跟踪账户级输出，例如：

- market_regime
- target_gross_exposure
- target_core_exposure
- target_tactical_exposure
- remaining_risk_budget
- crowded_exposures
- add_candidates
- trim_candidates
- blocked_candidates

## 15. 实现前置依赖

在开始实现 `regime_agent`、`portfolio_manager_agent` 和账户级决策流水线之前，项目需要先补齐一组最小前置依赖。这些内容不是可有可无的润色项，而是避免系统重新退化成“单票分析 + 组合话术”的基础层。

### 15.1 在更广泛实现前必须具备的前置项

#### 1. 账户状态输入结构

系统必须先定义统一的账户输入格式，否则无法进行仓位管理、回撤控制和组合层决策。

最低需要包含：

- 当前 NAV
- 可用现金
- 当前持仓列表
- 每笔持仓的市值、成本和浮盈亏
- 核心仓 / 战术仓分类
- 止损位或 thesis 失效位
- 最近净值高点或稳定的回撤计算基准

验收标准：

- 账户状态以结构化类型输入，而不是自由文本描述
- 系统能稳定计算总仓位、现金占比、核心仓占比、战术仓占比和当前回撤

#### 2. 持仓结构与候选池结构

系统必须区分“已有持仓复评”和“新机会评分”，否则无法做真正的账户级排序与阻断。

最低需要两类结构：

- `positions`：当前持仓
- `candidates`：待评估候选标的

每个标的至少应包含：

- ticker
- 市场
- 当前价格
- 预期账本类型（如已知）
- 主题 / 因子标签，第一版可人工维护
- 当前账户是否已有暴露

验收标准：

- 同一套评分流程既能处理持仓，也能处理新候选
- 组合层能清楚区分加仓、持有、减仓、退出，与新开仓、禁止新增两类动作

#### 3. 因子映射与代理暴露表

这是本系统面向该用户最关键的前置条件之一。没有这层映射，系统无法识别“不同 ticker，本质同一个方向”的隐藏集中度。

第一版不需要自动化，但必须先有可维护的人工映射表。

建议首批因子桶：

- BTC beta
- ETH beta
- mega-cap tech beta
- China ADR beta
- event-driven beta
- rate-sensitive beta

示例映射：

- MSTR → BTC beta
- SBET → ETH / treasury 风格 crypto beta
- PDD → China ADR beta

验收标准：

- 每个持仓和候选标的都能映射到 1 到 2 个主因子桶
- 系统能统计各因子桶当前暴露占比
- 组合层可以据此阻断隐藏的重复加仓

#### 4. 市场状态输入源

没有 regime 输入，系统就无法贯彻“先定账户进攻度，再决定是否准许交易”的核心设计。

第一版不需要复杂宏观模型，但必须有一套稳定、可重复的输入框架。

建议输入：

- 主要指数趋势代理
- 宽度或 leadership 代理
- 波动率代理
- 与用户重点主题相关的风险代理，例如 BTC、ETH

验收标准：

- 系统能稳定输出四种状态之一：Risk-On、Selective Risk-On、Neutral、Risk-Off
- 每种状态都能映射到默认的总仓与战术仓区间

#### 5. 单票评分卡 Schema

在组合层工作前，单票输出必须先从 LONG / SHORT 升级为结构化评分卡。

第一版最低需要：

- `trend_score`
- `entry_score`
- `valuation_stretch_score`
- `catalyst_score`
- `volatility_score`
- `correlation_penalty`
- `portfolio_fit_score`
- `recommended_book`
- `recommended_action`
- `invalidation_price`
- `suggested_position_range`

验收标准：

- 持仓和候选统一输出同一套 schema
- 组合层消费结构化字段，而不是解析自由文本 LONG / SHORT 结论

#### 6. 风险参数配置表

核心硬规则必须先落到配置层，而不是埋在 prompt 或散落在代码常量里。

最低应配置：

- 各市场状态下的总仓上限
- 各市场状态下的战术仓上限
- 核心仓 / 战术仓初始仓位建议
- 核心仓 / 战术仓单笔风险预算
- 因子暴露上限
- 预警 / 防守回撤阈值

验收标准：

- 所有关键阈值都可以集中查看和修改
- portfolio manager 输出引用同一套参数来源

### 15.2 第一轮实现中强烈建议同步补齐的能力

这些不一定阻塞第一行代码，但如果缺失，系统会很快进入“很难验证”的状态。

#### 7. NAV 与回撤计算逻辑

系统需要明确回撤逻辑：

- NAV 是按日频还是事件频跟踪
- 最近净值高点如何定义
- 是否纳入未实现盈亏
- 账户回撤与单票回撤是否分开处理

验收标准：

- 给定持仓和 NAV 时间序列，系统能稳定输出当前回撤与回撤分档
- 回撤分档能自动触发预警或防守模式

#### 8. 最小回放与场景验证框架

这个系统不仅要验证“分析对不对”，还要验证“账户决策安不安全”。

第一版不需要完整量化回测，先做场景回放就足够有价值。

最低能力：

- 读取样例账户状态
- 读取样例市场状态
- 读取一组候选评分卡
- 生成组合指令
- 验证是否违反硬约束

代表性场景至少包括：

- Risk-On 且仍可继续加风险
- Selective Risk-On 且主线狭窄
- Neutral 且机会质量分化
- Risk-Off 下即使单票强也被账户层阻断
- 多个 crypto proxy 导致集中度超限

#### 9. 稳定的账户经理输出模板

应尽早冻结第一版账户经理看板和交易建议单结构，避免后期输出层反复漂移。

最低模板包括：

- 账户经理看板字段
- 单票交易建议单字段
- blocked candidate 的解释字段
- forced trim 的解释字段

验收标准：

- 输出结构跨运行保持稳定
- 用户能直接看懂今天能不能加风险、该加什么、什么被阻断

### 15.3 可以后续渐进增强的项

这些重要，但不应阻塞价值最高的第一、第二阶段。

#### 10. 因子映射自动化

第一版可人工维护，后续再增强为：

- 基于规则的 symbol tagging
- 基于相关性的辅助归类
- 基于主题库的自动映射

#### 11. 券商或执行接口集成

第一阶段不需要自动下单。

后续再考虑：

- 自动同步持仓
- 导出订单建议
- 券商 API 联动

#### 12. 更完整的估值与基本面模块

初版应优先把精力放在：

- 趋势质量
- 入场质量
- 暴露重叠
- 组合风险预算

估值层第一版只需覆盖拉伸、过热和 premium risk 感知。

### 15.4 建议实现顺序

实现时应按以下顺序推进，而不是所有层并行摊开：

1. 账户与持仓数据结构
2. 候选池结构
3. 因子映射表
4. 单票评分卡 schema
5. 市场状态输入与状态机
6. 风险参数配置
7. 组合层阻断与约束逻辑
8. NAV 与回撤分档
9. 最小场景回放测试
10. 账户经理看板与交易建议单输出
11. 后续自动化层

### 15.5 实现准备度门槛

只有当下面这些内容具备后，才应视为真正进入实现阶段：

- `AccountState`
- `PositionState`
- `SingleNameScore`
- `PortfolioDirective`
- 可维护的候选池输入路径
- 第一版因子映射表
- 第一版市场状态输入层
- 统一风险参数配置源
- 最小场景测试集

如果这些还没有，项目大概率会重新滑回“单票分析引擎 + 组合描述文案”。

## 16. 最小改造的仓库演进策略

设计目标是尽量保留当前代码结构。

### 16.1 保留现有分析基础

继续保留：

- indicator agent
- pattern agent
- trend agent

它们仍然是底层分析引擎。

### 16.2 重定义当前决策层

当前 decision agent 不应继续扮演最终账户裁决者。

它应改造成 **single_name_scorer**，负责输出结构化评分卡。

### 16.3 新增上层模块

新增模块建议包括：

- `regime_agent`
- `portfolio_manager_agent`
- `risk_mapper`

这样可以在不推翻现有单票逻辑的前提下，逐步加出上层经理能力。

## 17. TradingGraph 演进路径

当前 `core/trading_graph.py` 是顺序执行单票结论。

目标演进如下：

### 阶段 A：单票分析流水线

对每个候选标的或当前持仓执行：

- 指标分析
- 形态分析
- 趋势分析
- 单票评分

### 阶段 B：组合决策流水线

把以下内容统一输入到账户层：

- 市场状态
- 账户状态
- 当前持仓
- 候选标的评分卡
- 持仓复评评分卡

最终输出完整的账户级指令。

系统将从：

- 一只股票输入，一个结论输出

演进为：

- 账户上下文 + 多只股票输入，输出组合指令 + 单票交易建议单

## 18. 渐进式实现路径

为了控制复杂度，建议分三阶段落地，其中第一、第二阶段承载了绝大部分实际价值。

### 阶段 1：标准化输入，并升级单票输出

这是价值最高的第一步，因为它在不立即引入完整组合层的前提下，就能把现有引擎升级成可被后续账户层消费的标准化模块。

先做：

- 建立 `AccountState` 和 `PositionState`
- 定义候选池输入结构
- 建立第一版因子映射表
- 把 LONG / SHORT 改成结构化评分卡
- 给每只机会做核心仓 / 战术仓归类
- 增加仓位、失效价和交易结构输出

这一阶段产出的是后续所有账户层都依赖的标准化输入与输出。

### 阶段 2：加入账户上下文和经理看板

这是第二个高价值阶段，因为它把系统从“更好的单票分析器”推进成“真正可用的账户助手”。

引入：

- 账户与持仓输入流程
- 总仓、现金、核心仓、战术仓统计
- 简单的因子暴露统计
- 市场状态评估
- 账户级风险预算与回撤分档
- 第一版账户经理看板

到这一步，系统就能回答：

- 今天账户还能不能加风险？
- 应该加哪类风险，避免哪类风险？
- 当前是否已经在某个隐藏因子桶中过于拥挤？

### 阶段 3：加入严格组合约束与更强经理输出

引入：

- 相关性感知阻断
- 因子组暴露上限
- 回撤触发的自动降风险逻辑
- blocked candidate / forced trim 等经理输出

完成这一阶段后，系统才真正成为“实盘 + 经理型”的组合助手。

## 19. 测试策略

测试应同时覆盖“分析正确性”和“决策安全性”。

### 19.1 单票评分测试

验证：

- 评分卡 schema 是否完整稳定
- 典型 setup 下的输出是否稳定
- 标的被归类到核心仓 / 战术仓是否合理

### 19.2 账户状态测试

验证：

- 回撤计算是否正确
- 核心仓 / 战术仓占用是否正确
- 现金和总暴露统计是否正确

### 19.3 组合经理测试

验证：

- 不同市场状态下的仓位上限是否生效
- 因子集中度是否能被识别
- 当账户级限制超标时是否阻断新仓
- 回撤进入不同阈值后是否正确降档

### 19.4 端到端场景测试

典型场景至少包括：

- 强 Risk-On 环境，允许继续加风险
- 领导主线狭窄，仅允许选择性进攻
- Neutral 环境下，单票信号分化
- 防守环境下，单票仍强但账户层阻断新增
- 多个 crypto-proxy 持仓导致相关性阻断

## 20. 错误处理与边界行为

该设计不追求到处堆砌 fallback，而是保持实用和聚焦。

边界校验应主要施加在：

- 用户输入的账户与持仓数据
- 外部获取的市场数据
- 标的因子映射等可选输入

系统内部模块之间应尽量依赖一致的类型化结构，而不是大量防御性分支去处理理论上不会发生的状态。

## 21. 第一阶段非目标

第一阶段实现不应试图一次解决所有组合管理问题。

不属于首阶段目标的内容包括：

- 完整港股支持
- 为每家公司都接入基本面模型
- 期权组合管理
- 税务优化
- 机构级优化器数学求解
- 面向所有资产类别的过度泛化支持

第一阶段应严格聚焦用户当前真实工作流。

## 22. 最终设计总结

项目应从“单票技术分析引擎”演进为“面向个人美股账户、具备组合感知能力的实盘交易系统”。

最终结构应为：

- 底层：把趋势、形态、指标分析转成结构化单票评分卡
- 上层：加入市场状态、账户状态、因子暴露和组合风险管理
- 输出层：同时提供账户经理看板和可执行交易建议单

整个系统最核心的设计规则是：

> 一只股票单独看可以很有吸引力，但放到当前账户里，仍可能是错误的交易。

这条规则就是整个系统的核心，也应成为后续实现计划的指导原则。
